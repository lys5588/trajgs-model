CLS 是首版的工程基线，还没有证据表明它最适合相机轨迹任务。
Patch 特征保留可索引的空间网格，但不能补回裁剪时丢失的原图构图。

当前只实现了 CLS 路径。下文的 patch、bbox 几何与 cross-attention 均为候选方案。
本页不给出训练效果结论，也不修改模型或配置。

## A 为什么首版选择 CLS

我们需要先跑通每帧一个视觉向量的双编码器。
CLS 可直接经 Linear 投影，再与同一时刻的相机特征拼接。
这让时序主干保留 20 个 token，与原有 VAE 接口一致。

| 首版选择的原因 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| 一个裁剪图对应一个向量 | 数据对齐与接口简单 | 不能证明空间信息足够 |
| 768→256 投影 | 与相机 256 维特征直接拼接 | 不能证明此压缩最优 |
| 时序主干仅处理 20 步 | 下游计算量较小 | 不能证明轨迹生成质量更高 |
| 沿用双后验框架 | 方便验证架构与梯度 | 不能证明模型已利用视觉信息 |

DINOv3 同时提供 CLS 和 patch 特征。
官方还列出了分类、对应关系、深度和分割等使用方式。
因此“使用 DINOv3”不要求只取 CLS。[官方模型卡](https://github.com/facebookresearch/dinov3/blob/main/MODEL_CARD.md)

我们当前通过的是结构测试，尚未得到预训练视觉特征的任务消融结果。

## B 空间信息在哪一步丢失

需要区分三种“空间”。

| 空间类型 | 例子 | CLS | 196 个 patch |
| --- | --- | --- | --- |
| 裁剪图内部二维布局 | 目标左侧部件、表面纹理、局部遮挡 | 可能隐含部分信息，不能按位置直接读取 | 保留 14×14 索引，便于局部读取 |
| 原图中的构图 | 目标偏左还是偏右、占画面比例 | 仅靠裁剪特征不能可靠恢复 | 同样不能，仅有裁剪内坐标 |
| 场景三维关系 | 距离、真实尺度、遮挡物位置 | 没有显式三维几何保证 | 局部对应线索更可用，但仍无几何保证 |

```flow TB
完整原图与 bbox -> bbox 裁剪并拉伸
bbox 裁剪并拉伸 -> 只保留目标裁剪图\n原图位置与范围未输入网络
只保留目标裁剪图\n原图位置与范围未输入网络 -> DINOv3
DINOv3 -> CLS\n聚合表示 768
DINOv3 -> Patch 网格\n14 × 14 × 768
CLS\n聚合表示 768 -> 当前投影 768→256\n进一步压缩
Patch 网格\n14 × 14 × 768 -> 可按区域选择与融合\n仍不能恢复裁剪外背景
```

“同一目标在原图左边”和“在原图右边”可能产生相同裁剪图。
模型即使读取全部 patch，也无法据此区分原图位置。

CLS 不等于“完全没有空间信息”。
它可能编码视角、形状与布局，但这些信息混合在一个向量中。
它不提供“第 r 行第 c 列”的显式访问接口。

Patch 也不是无损像素或现成的 3D 点。
各 patch 已通过 DINO 自注意力混入整张裁剪图的上下文。
相邻帧中相同的 patch 索引，也不保证对应同一个物体表面点。

## C 当前 CLS 方式 · 先聚合，再融合相机

记 C_t 为 256 维相机投影，s_t 为 768 维 CLS。
DINOv3 内部的 CLS 聚合不读取我们的相机特征。
当前冻结骨干，这个聚合规则也不会随轨迹任务更新。

```flow TB
第 t 帧裁剪图 -> 冻结 DINOv3\nCLS 768
冻结 DINOv3\nCLS 768 -> 可训练视觉 Linear\n768 → 256
第 t 帧相机 D -> 相机 Linear 与时间 PE\nD → 256
可训练视觉 Linear\n768 → 256 -> concat\n第 t 帧 512 维
相机 Linear 与时间 PE\nD → 256 -> concat\n第 t 帧 512 维
concat\n第 t 帧 512 维 -> 联合时序 Transformer\nB × 20 × 512
联合时序 Transformer\nB × 20 × 512 -> mu 与 logvar\n各 20 × B × 256
```

| 属性 | 当前 CLS 路径 |
| --- | --- |
| 骨干输出 | [B,20,768] |
| 视觉投影 | [B,20,256] |
| 相机投影 | [B,20,256] |
| 融合 | 按通道 concat，得到 [B,20,512] |
| 空间汇聚位置 | 相机融合之前，已由 CLS 汇聚 |
| 主要用途假设 | 每帧的目标整体外观与粗粒度视角信息 |

对于物体身份、整体外观提示，CLS 是合理基线。
对于局部部件展示、遮挡边界、精细视角约束，空间汇聚可能过早。
这些是结构层面的判断，实际影响仍需实验确认。

768 维是否“够用”不能仅由维度决定。
当前下游真正使用的视觉向量还是投影后的 256 维。

## D 保留 Patch · 与相机特征不能直接照搬拼接

完整 patch 序列形状为 [B,20,196,768]。
多出的 196 是空间 token 轴，与相机的 [B,20,256] 不直接匹配。

### 方式一：每个 patch 配上同一帧相机特征

```flow TB
Patch 特征\nB × 20 × 196 × 768 -> 逐 patch Linear 768→256
相机特征\nB × 20 × 256 -> 每帧复制到 196 个位置
逐 patch Linear 768→256 -> 按通道拼接\nB × 20 × 196 × 512
每帧复制到 196 个位置 -> 按通道拼接\nB × 20 × 196 × 512
按通道拼接\nB × 20 × 196 × 512 -> 展平时空 token\nB × 3920 × 512
展平时空 token\nB × 3920 × 512 -> 时空 Transformer\n需要时间与空间位置表示
时空 Transformer\n需要时间与空间位置表示 -> 再按帧汇聚或重采样\n恢复 20 个 latent 位置
```

这种方案让不同帧、不同区域直接交互。
但会显著增加时序主干的序列长度。
若仍要求 Decoder 接收 20 个 latent，末端还需空间汇聚。

也可以把相机当作额外 token，与每帧 196 个 patch 拼接。
此时每帧 197 个 token，整段为 3940 个；这属于 token 拼接。
它与当前的“两个 256 维向量沿通道拼成 512”是不同操作。

仅把 patch 取平均再投影，仍然会提前丢掉显式空间轴。
这可以作为池化对照，但不等同于保留 patch 供融合模块读取。

## E 推荐比较的候选 · 相机查询 Patch，再做时序

先把每个 patch 投影到 256 维。
用同一时刻的相机特征作为 Query，patch 特征作为 Key/Value。
Cross-attention 输出一个与该相机条件有关的视觉摘要。

```flow TB
第 t 帧 Patch\n196 × 768 -> 逐 patch Linear 与二维位置表示\n196 × 256
第 t 帧相机特征\n1 × 256 -> Query 投影\n1 × 256
逐 patch Linear 与二维位置表示\n196 × 256 -> Key 与 Value\n各 196 × 256
Query 投影\n1 × 256 -> 同帧 cross-attention\n1 个 query 读取 196 个 patch
Key 与 Value\n各 196 × 256 -> 同帧 cross-attention\n1 个 query 读取 196 个 patch
同帧 cross-attention\n1 个 query 读取 196 个 patch -> 相机条件视觉摘要\n1 × 256
相机条件视觉摘要\n1 × 256 -> 与相机 256 维拼接\n每帧 512 维
第 t 帧相机特征\n1 × 256 -> 与相机 256 维拼接\n每帧 512 维
与相机 256 维拼接\n每帧 512 维 -> 现有 20 步时序主干\nB × 20 × 512
```

| 对比点 | CLS 当前方案 | Patch 查询候选 |
| --- | --- | --- |
| 先读到什么 | 已汇聚的全局向量 | 196 个可索引区域特征 |
| 相机参与的时机 | 空间汇聚之后 | 空间汇聚时 |
| 区域权重来源 | 冻结 DINO 的 CLS 聚合 | 可训练的相机条件 cross-attention |
| 最终每帧视觉宽度 | 256 | 256 |
| 后续时序 token 数 | 20 | 20 |
| Decoder 接口 | [20,B,256] latent | 可保持一致 |

候选方案仍将空间信息压缩成一个向量，并非无损保留全部 patch。
区别在于延后汇聚，让轨迹任务学习如何读取区域。
一个 Query 未必足够；后续可比较每帧 4 个 Query，但不是本轮定案。
两种特征也可共用：保留 CLS，再加入 patch 查询结果。
此时需要将全局与局部结果融合，并控制新增参数。

DINO 内部已有 2D RoPE，patch 特征也包含位置相关上下文。
下游仍建议显式提供二维 patch 坐标。
仅保留数组顺序，不等于新 attention 自动理解二维布局。

这是一种待验证设计推断，不是 DINOv3 论文的相机轨迹实验结论。

## F 构图与三维几何 · CLS 和 Patch 都需要补充什么

对于“主体靠左”“保持占比”，建议把原图 bbox 几何显式传入。
可用实际裁剪框构造归一化向量：

```text title="候选 bbox 几何表示"
g_t = [center_x / W, center_y / H, box_width / W, box_height / H]
```

| 任务需要 | 可考虑的补充 | 能补什么 |
| --- | --- | --- |
| 原图构图 | bbox 中心与宽高 g_t | 主体在画面的位置和占比 |
| patch 的原图位置 | 裁剪内坐标 + 实际裁剪框 + 原图尺寸 | 把局部网格映射回原图 |
| 周边障碍物与背景 | 全图特征或场景上下文 | bbox 外信息 |
| 距离、遮挡与可见性 | 重建场景的深度或几何查询 | 显式三维约束与观测 |

相机 9D/11D 含位姿和 FOV，但不含目标在画面中的 bbox。
仅给相机参数，不会自动给出目标位置和大小。

Patch 对应关系是潜在线索，不保证真实尺度或稳定的三维匹配。
DINOv3 的稠密特征适用于多种空间任务；这不等于本任务已获得几何保证。
依据：[DINOv3 论文](https://arxiv.org/abs/2508.10104)、
[官方模型卡](https://github.com/facebookresearch/dinov3/blob/main/MODEL_CARD.md)。

## G 计算量 · 保留 Patch 不等于重复跑 DINO

当前 DINO forward 已计算 CLS 与 patch 特征。
改为读取 patch，不需要为同一张图重新运行一次骨干。
主要增量来自下游投影、融合、保存特征和时序注意力。

令 T=20、P=196。下面只计算单层、单头的注意力关联数。

| 下游方式 | 关联数 | 计算含义 |
| --- | --- | --- |
| 当前 20 步时序自注意力 | 20² = 400 | 每帧一个融合 token |
| 3920 个时空 token 全连接 | 3920² = 15366400 | 每个 patch 配相机并展平，约为上行 38416 倍 |
| 每帧 1 Query 读取 196 Patch | 20×1×196 = 3920 | 新增的同帧 cross-attention |
| 上行之后的时序自注意力 | 20² = 400 | 仍保持 20 步 |

这不是端到端速度或显存倍数。
投影、FFN、层数、head 数和 DINO 本身都未计入。
实际实现也不一定显式存储整个注意力矩阵。

每帧缓存的原始视觉元素由 768 变为 196×768。
缓存占用是 196 倍；不代表整个模型显存也是 196 倍。

## H 对本项目的判断与后续对照

我的判断：CLS 应保留为基线；空间敏感任务值得测试 patch 条件汇聚。
原图构图首先需要 bbox 几何；仅换 patch 无法解决这部分缺失。

建议未来用三组对照分离两种影响：

| 组别 | 视觉输入与融合 | 要回答的问题 |
| --- | --- | --- |
| A | 当前 CLS → 256 → concat 相机 | 当前简单基线能做到什么 |
| B | CLS + bbox 几何 → 256 → concat 相机 | 补回构图几何是否已经足够 |
| C | Patch + 二维坐标 + bbox 几何，经相机 Query 汇聚 | 局部区域读取是否带来额外收益 |

各组保持同一 DINO 权重、数据划分、20 步与 256 维 latent。
对齐训练预算，并报告新增参数和真实耗时，避免只比较 token 数。

在编码器阶段，可检查相机重建、视觉置零与图像错配消融。
若打乱图像对结果几乎无影响，需要检查模型是否真正使用视觉。
联合编码器已读入完整相机序列，单看重建误差不足以证明视觉有效。
增加 patch 数量本身不能解决训练目标对视觉依赖不足的问题。

完整轨迹生成阶段，再比较渲染后的主体中心误差、占比和可见性。
轨迹平滑性与文本指令遵循还需后续生成器与训练，当前不能下结论。

目前两个编码器学习 q(z|camera) 与 q(z|camera,image)。
相机 Query 在这里读取的是已提供的训练轨迹特征。
最终生成时不能直接假设未知目标相机已可用；那是后续条件设计。
